## 3. 🔴 Critique

### A-01 — Le plancher calorique est contourné pour « maintien » et « prise »

**Où** : `frontend/features/goals/calculations.ts` (fonction
`calculateCompleteTargets`, autour de la ligne 265).

```ts
const floorApplied = goal.type === 'loss' && rawCalories < floor;
```

**Le problème.** Le plancher de sécurité (jamais sous le métabolisme de base,
ni sous 1 200 kcal pour une femme / 1 500 pour un homme) n'est appliqué que si
l'objectif est de type `loss`. Or `rawCalories` inclut
`calorie_adjustment_kcal`, qui peut descendre jusqu'à **−1 000 kcal**
(`ADJUSTMENT_LIMIT_KCAL` dans `frontend/features/stats/calorieAdjustment.ts`).
Sur un objectif « maintien » ou « prise », rien ne rattrape la valeur.

**✅ Corrigé.**

**Rectification de l'audit.** La première version de cette section donnait
comme déclencheur « un ajustement de −1 000 kcal ». C'était un cas construit à
la main : par le flux de suggestion, il est **inatteignable**, parce que
`suggestCalorieAdjustment` borne elle-même sa proposition au plancher.

Le vrai chemin, trouvé en écrivant les tests, est **un changement de profil
après l'acceptation d'un ajustement**. Les calories de la formule sont
recalculées depuis le profil à chaque affichage, mais `calorie_adjustment_kcal`
reste figé sur l'objectif. Une personne qui accepte « manger 285 kcal de moins »
à 95 kg, puis descend à 42 kg, se retrouve avec une formule bien plus basse et
le même ajustement :

```text
plancher : 1200 kcal
type=maintain  => cible 792 kcal  ⚠ SOUS LE PLANCHER
type=gain      => cible 993 kcal  ⚠ SOUS LE PLANCHER
```

C'est ce que vérifie le test
`calorieAdjustment.test.ts` → « le plancher protège tous les types après un
changement de profil ». Le type `loss` est exclu de ce test : le plancher s'y
appliquait déjà, donc aucune baisse n'est jamais proposée pour ce profil.

**Deuxième défaut, lié.** `suggestCalorieAdjustment()` applique de son côté le
plancher à **tous** les types d'objectif :

```ts
const proposedKcal = Math.max(floor, formulaKcal + newAdjustmentKcal);
```

L'aperçu promet donc une valeur (par ex. 1 200 kcal) que
`calculateCompleteTargets` ne respectera pas après enregistrement. **L'aperçu
et la cible réelle ne disent pas la même chose.**

C'est le problème le plus grave de l'audit : l'application peut proposer un
apport dangereusement bas sur une application de santé.

**Correctif.** Appliquer le plancher quel que soit le type d'objectif. Pour
« prise », le plancher ne se déclenchera jamais (la cible est au-dessus du
TDEE) : le comportement actuel est donc conservé partout où il était correct.

```ts
// frontend/features/goals/calculations.ts
- const floorApplied = goal.type === 'loss' && rawCalories < floor;
+ // Le plancher protège aussi « maintien » et « prise » : l'ajustement
+ // (jusqu'à −1 000 kcal) pouvait sinon faire tomber la cible sous le
+ // métabolisme de base.
+ const floorApplied = rawCalories < floor;
```

**Tests à écrire d'abord (TDD)** dans `calculations.test.ts` :

1. `maintain` + `calorie_adjustment_kcal: -1000` → cible `=== getCalorieFloor(...)`
   et `calorie_floor_applied === true` ;
2. `gain` + ajustement très négatif → même attente ;
3. non-régression : `gain` sans ajustement → cible inchangée, `calorie_floor_applied` absent ;
4. cohérence : pour les trois types, `calculateCompleteTargets(...).calories_kcal`
   doit égaler le `proposedTargetKcal` annoncé par `suggestCalorieAdjustment`.

### A-02 — Les photos de profil sont lisibles par n'importe qui

**Où** : `backend/supabase/migrations/20251205192400_add_profile_fields.sql`
lignes 38-56.

```sql
INSERT INTO storage.buckets (id, name, public)
VALUES ('profile-pictures', 'profile-pictures', true)   -- bucket PUBLIC
...
CREATE POLICY "Everyone can view profile pictures"
  ON storage.objects FOR SELECT
  USING (bucket_id = 'profile-pictures');               -- aucun TO, aucun contrôle
```

**Le problème.** Deux faiblesses qui se cumulent :

1. le bucket est déclaré `public = true` : les fichiers sont servis sans jeton ;
2. la politique `SELECT` n'a **ni clause `TO`** (elle s'applique donc au rôle
   `PUBLIC`, visiteurs anonymes compris) **ni contrôle de propriétaire**.

Conséquence : la politique autorise aussi l'**API de listage**. Quelqu'un qui
connaît l'identifiant d'un utilisateur peut lister son dossier
(`<user_id>/`), y lire le nom exact du fichier
(`avatar-<horodatage>.jpg`, généré dans
`frontend/features/profile/profilePhoto.service.ts:42`) puis télécharger la
photo. Le nom contient un horodatage, donc il n'est pas devinable — mais le
listage supprime justement cette protection.

Sur une application de santé, une photo de visage est une donnée personnelle :
elle ne devrait pas être atteignable sans être connecté et propriétaire.

**Correctif** — nouvelle migration (ne jamais modifier une migration déjà
appliquée) :

```sql
-- backend/supabase/migrations/<horodatage>_private_profile_pictures.sql
-- Les photos de profil ne sont plus servies publiquement : chacun ne lit que
-- les siennes, via une URL signée de courte durée.

UPDATE storage.buckets SET public = false WHERE id = 'profile-pictures';

DROP POLICY IF EXISTS "Everyone can view profile pictures" ON storage.objects;

CREATE POLICY "Users can view own profile pictures"
  ON storage.objects FOR SELECT
  TO authenticated
  USING (
    bucket_id = 'profile-pictures'
    AND (storage.foldername(name))[1] = (SELECT auth.uid())::text
  );

-- La suppression manquait aussi : sans elle, l'ancienne photo et le nettoyage
-- avant suppression de compte échouent silencieusement (voir A-26).
DROP POLICY IF EXISTS "Users can delete own profile pictures" ON storage.objects;
CREATE POLICY "Users can delete own profile pictures"
  ON storage.objects FOR DELETE
  TO authenticated
  USING (
    bucket_id = 'profile-pictures'
    AND (storage.foldername(name))[1] = (SELECT auth.uid())::text
  );
```

**Côté application**, remplacer l'URL publique par une URL signée :

```ts
// frontend/features/profile/profilePhoto.service.ts
- const { data } = supabase.storage.from(PROFILE_PHOTOS_BUCKET).getPublicUrl(path);
- await setProfilePhotoUrl(userId, data.publicUrl);
- return data.publicUrl;
+ // On stocke le CHEMIN, pas une URL : les URL signées expirent.
+ await setProfilePhotoUrl(userId, path);
+ return path;
```

puis, à l'affichage (`Avatar.tsx` / `IdentityCard.tsx`), obtenir l'URL au
moment du rendu :

```ts
const { data } = await supabase.storage
  .from(PROFILE_PHOTOS_BUCKET)
  .createSignedUrl(path, 3600); // 1 h
```

⚠️ **Migration des données existantes** : `profiles.profile_picture_url`
contient aujourd'hui des URL complètes. `photoPathFromUrl()` sait déjà extraire
le chemin : garder cette fonction et accepter les deux formes pendant une
version (si la valeur contient `/object/public/`, en extraire le chemin),
le temps que les profils existants soient migrés.

**Attention** : cette migration touche la base de production. À appliquer
seulement avec ton accord explicite, et à tester d'abord sur une branche
Supabase.

### A-03 — Aucun garde-fou React : une erreur d'affichage = écran blanc

**Où** : nulle part — recherche de `componentDidCatch`,
`getDerivedStateFromError` et `ErrorBoundary` : **aucun résultat**.

**Le problème.** En React, une erreur levée pendant le rendu démonte tout
l'arbre. Sans « Error Boundary », l'utilisateur voit une page **entièrement
blanche**, sans message, sans bouton. Sur une PWA installée sur téléphone,
c'est la pire issue possible : l'application semble cassée définitivement, et
le rechargement n'est pas évident (il faut fermer et rouvrir l'application).

**Correctif** — un composant à créer, puis à placer autour de `<App />` :

```tsx
// frontend/app/AppErrorBoundary.tsx
import { Component, ReactNode } from 'react';

interface Props { children: ReactNode }
interface State { hasError: boolean }

/**
 * Dernier filet de sécurité : si un écran lève une erreur, on affiche un
 * message clair et un bouton de rechargement au lieu d'une page blanche.
 */
export class AppErrorBoundary extends Component<Props, State> {
  state: State = { hasError: false };

  static getDerivedStateFromError(): State {
    return { hasError: true };
  }

  componentDidCatch(error: Error) {
    // Visible dans la console du navigateur ; à relier au suivi d'erreurs (A-25)
    console.error('Erreur non rattrapée :', error);
  }

  render() {
    if (!this.state.hasError) return this.props.children;
    return (
      <div role="alert" className="min-h-screen flex items-center justify-center p-6 bg-surface">
        <div className="max-w-md space-y-4 text-center">
          <h1 className="card-title">Une erreur est survenue</h1>
          <p className="text-muted">
            Vos données sont intactes. Rechargez la page pour continuer.
          </p>
          <button
            type="button"
            onClick={() => window.location.reload()}
            className="btn-primary"
          >
            Recharger CalTrack
          </button>
        </div>
      </div>
    );
  }
}
```

```tsx
// frontend/app/main.tsx
<AppErrorBoundary>
  <App />
</AppErrorBoundary>
```

**Test** : un composant enfant qui lève une erreur → le message et le bouton
sont affichés (penser à faire taire `console.error` dans ce test).

### A-04 — 24 politiques RLS re-évaluées à chaque ligne, et une politique en double

**Où** : `backend/supabase/migrations/20251023212206_create_calorie_tracker_schema.sql`
(lignes 179-278) et `20251203191737_20251203_create_profiles_and_password_reset.sql`
(lignes 60-71).

**Le problème.** Les politiques écrites au début du projet utilisent
`auth.uid()` directement :

```sql
USING (user_id = auth.uid())           -- recalculé pour CHAQUE ligne
```

Postgres ne peut pas sortir cet appel de la boucle : sur une table de plusieurs
milliers d'entrées, la fonction est appelée autant de fois. Les migrations plus
récentes (recettes, eau, préférences) utilisent déjà la bonne forme
`(SELECT auth.uid())`, qui n'est évaluée **qu'une fois**. Les advisors Supabase
signalent **24 politiques** encore à l'ancienne forme, sur `profiles`, `goals`,
`daily_targets`, `foods`, `entries` et `weight_logs`.

Deuxième point : `profiles` a **deux** politiques `SELECT` qui font la même
chose (`Users can view own profile` et `Users can read own profile`, créées par
deux migrations différentes). Les deux sont évaluées à chaque lecture, et la
redondance rend la sécurité plus difficile à relire.

Ce n'est **pas** une faille : l'isolation des données fonctionne. C'est de la
performance et de la lisibilité.

**Correctif** — une nouvelle migration qui recrée les politiques :

```sql
-- backend/supabase/migrations/<horodatage>_rls_select_auth_uid.sql
-- Même règle, écriture optimisée : (SELECT auth.uid()) n'est évalué qu'une
-- fois par requête au lieu d'une fois par ligne.
-- Supprime aussi le doublon de politique SELECT sur profiles.

-- profiles : une seule politique de lecture
DROP POLICY IF EXISTS "Users can view own profile" ON profiles;
DROP POLICY IF EXISTS "Users can read own profile" ON profiles;
CREATE POLICY "Users can read own profile"
  ON profiles FOR SELECT TO authenticated
  USING (id = (SELECT auth.uid()));

DROP POLICY IF EXISTS "Users can insert own profile" ON profiles;
CREATE POLICY "Users can insert own profile"
  ON profiles FOR INSERT TO authenticated
  WITH CHECK (id = (SELECT auth.uid()));

DROP POLICY IF EXISTS "Users can update own profile" ON profiles;
CREATE POLICY "Users can update own profile"
  ON profiles FOR UPDATE TO authenticated
  USING (id = (SELECT auth.uid()))
  WITH CHECK (id = (SELECT auth.uid()));

-- … répéter pour goals, daily_targets, entries, weight_logs
-- (USING (user_id = (SELECT auth.uid())))
-- et pour foods, en gardant les aliments publics :
--   USING (is_public = true OR user_id = (SELECT auth.uid()))
```

**Vérification** : `backend/supabase/tests/02_rls_isolation.sql` doit rester
vert (il prouve que l'isolation ne change pas), puis relancer les advisors de
performance : les 24 alertes `auth_rls_initplan` et l'alerte
`multiple_permissive_policies` doivent disparaître.

Procédure projet : écrire le fichier, l'appliquer avec `apply_migration`, puis
**renommer le fichier** avec la version enregistrée par Supabase.

### A-05 — Le focus s'échappe de la modale d'ajout d'aliment

**Où** : `frontend/features/journal/AddEntryModal.tsx` (ligne 892 :
`role="dialog" aria-modal="true"` ; Échap géré ligne 441).

**Le problème.** La modale principale de l'application annonce
`aria-modal="true"` mais **ne retient pas le focus** : avec la touche Tab, on
sort de la fenêtre et on atteint les boutons de la page derrière, qu'un
lecteur d'écran est censé ignorer. Le motif ARIA « dialog » exige que le focus
reste contenu.

Trois manques, sur les trois modales (`AddEntryModal`, `WhatsNewDialog`,
`GuidedTour`) :

| Comportement attendu | AddEntryModal | WhatsNewDialog | GuidedTour |
| --- | --- | --- | --- |
| Échap ferme | ✅ | ✅ | ✅ |
| Tab reste dans la fenêtre | ❌ | ⚠️ `<button>` seuls | ⚠️ `<button>` seuls |
| Focus rendu au bouton d'origine | ❌ | ❌ | ❌ |
| Défilement de la page bloqué | ❌ | ❌ | ❌ |

**Pourquoi les 64 tests axe ne le voient pas** : axe analyse le DOM d'un
instant donné. Il ne simule pas la touche Tab et ne sait donc pas détecter un
piège de focus manquant ni une absence de restauration du focus. C'est un
angle mort de la suite, pas un oubli des tests.

**Correctif** — un hook partagé, qui corrige les trois modales d'un coup et
servira à la quatrième (la fenêtre « Copier un repas », prévue en 2.3.0) :

```ts
// frontend/shared/ui/useModalFocus.ts
import { useEffect, RefObject } from 'react';

/** Tous les éléments réellement atteignables au clavier (pas seulement les boutons). */
const FOCUSABLE =
  'a[href], button:not([disabled]), input:not([disabled]), select:not([disabled]), ' +
  'textarea:not([disabled]), [tabindex]:not([tabindex="-1"])';

/**
 * Accessibilité d'une fenêtre modale :
 * 1. Tab et Maj+Tab tournent à l'intérieur de la fenêtre ;
 * 2. le focus revient à l'élément qui l'a ouverte à la fermeture ;
 * 3. la page derrière ne défile plus.
 */
export function useModalFocus(ref: RefObject<HTMLElement | null>, onClose: () => void) {
  useEffect(() => {
    const opener = document.activeElement as HTMLElement | null;
    const previousOverflow = document.body.style.overflow;
    document.body.style.overflow = 'hidden';

    const onKeyDown = (event: KeyboardEvent) => {
      if (event.key === 'Escape') {
        event.preventDefault();
        onClose();
        return;
      }
      if (event.key !== 'Tab' || !ref.current) return;
      const items = Array.from(ref.current.querySelectorAll<HTMLElement>(FOCUSABLE)).filter(
        (item) => item.offsetParent !== null
      );
      if (items.length === 0) return;
      const first = items[0];
      const last = items[items.length - 1];
      if (event.shiftKey && document.activeElement === first) {
        event.preventDefault();
        last.focus();
      } else if (!event.shiftKey && document.activeElement === last) {
        event.preventDefault();
        first.focus();
      }
    };

    document.addEventListener('keydown', onKeyDown);
    return () => {
      document.removeEventListener('keydown', onKeyDown);
      document.body.style.overflow = previousOverflow;
      opener?.focus();
    };
  }, [ref, onClose]);
}
```

Attention dans `AddEntryModal` : la gestion actuelle d'Échap tient compte de
`submitting` (on ne ferme pas pendant un enregistrement). Passer donc un
`onClose` qui conserve ce garde-fou.

**Tests** (avec `@testing-library/user-event`, qui simule vraiment Tab) :
Tab depuis le dernier élément revient au premier ; Maj+Tab depuis le premier va
au dernier ; après fermeture, `document.activeElement` est le bouton d'origine.

### A-07 — Aucun en-tête de sécurité HTTP

**Où** : `netlify.toml` — les sections `[[headers]]` ne gèrent que le cache.

**Le problème.** Aucun de ces en-têtes n'est envoyé :
`Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`,
`Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security`.

C'est d'autant plus important ici que **le jeton de session Supabase est stocké

```toml
# localStorage, une CSP limite fortement l'impact d'une injection de script).
[[headers]]
  for = "/*"
  [headers.values]
    X-Frame-Options = "DENY"
    X-Content-Type-Options = "nosniff"
    Referrer-Policy = "strict-origin-when-cross-origin"
    Permissions-Policy = "camera=(self), microphone=(), geolocation=()"
    Strict-Transport-Security = "max-age=31536000; includeSubDomains"
    Content-Security-Policy = """
      default-src 'self'; \
      script-src 'self' 'wasm-unsafe-eval'; \
      style-src 'self' 'unsafe-inline'; \
      img-src 'self' data: blob: https://images.openfoodfacts.org https://*.supabase.co; \
      connect-src 'self' https://*.supabase.co wss://*.supabase.co; \
      font-src 'self'; \
      worker-src 'self'; \
      frame-ancestors 'none'; \
      base-uri 'self'; \
      form-action 'self'"""
```

**À vérifier avant de mettre en production**, dans une **prévisualisation de
PR** (gratuite) et la console du navigateur ouverte :

- `camera=(self)` : le scanner de code-barres doit encore fonctionner ;
- `'wasm-unsafe-eval'` : nécessaire pour ZXing (WebAssembly) ;
- `style-src 'unsafe-inline'` : Tailwind et les styles en ligne de React en ont

### A-09 — Enregistrer un aliment deux fois de suite provoque une erreur brute

**Où** : `frontend/features/foods/foods.service.ts`, `savePersonalFood()`.

**Le problème.** La fonction fait « je cherche, puis j'insère » :

```ts
const { data: existing } = await supabase.from('foods').select('id')
  .eq('user_id', userId).eq('barcode', payload.barcode).maybeSingle();
if (existing) { /* update */ }
// sinon insert
```

Entre la lecture et l'insertion, une autre requête peut avoir créé la ligne
(double appui sur « Enregistrer », deux onglets ouverts). Or il existe un index
unique en base :

```sql
-- 20261108170840_food_library.sql
CREATE UNIQUE INDEX foods_user_barcode_key ON foods (user_id, barcode)
  WHERE user_id IS NOT NULL AND barcode IS NOT NULL;
```

L'insertion échoue donc avec une erreur Postgres `23505` brute, remontée telle
quelle à l'utilisateur — exactement ce que la validation côté client cherche à
éviter ailleurs dans le projet.

**Correctif.** Laisser Postgres faire le travail, en une seule requête :

```ts
export async function savePersonalFood(
  userId: string, values: PortionValues, barcode?: string | null, estimated = false
): Promise<Food> {
  const payload = buildPersonalFoodPayload(userId, values, barcode, estimated);

  // Un code-barres ne correspond qu'à un seul de vos aliments : on laisse
  // Postgres arbitrer (l'index unique foods_user_barcode_key), ce qui évite
  // la course entre la lecture et l'insertion.
  if (payload.barcode) {
    const { data, error } = await supabase
      .from('foods')
      .upsert(payload, { onConflict: 'user_id,barcode' })
      .select()
      .single();
    if (error) throw error;
    return data as Food;
  }

  const { data, error } = await supabase.from('foods').insert(payload).select().single();
  if (error) throw error;
  return data as Food;
}
```

**Test** : deux appels successifs avec le même code-barres → une seule ligne,
valeurs du second appel, aucune erreur. (Le faux Supabase des tests devra
gérer `upsert`.)

### A-10 — Le proxy Open Food Facts est ouvert à tous

**Où** : `backend/netlify/functions/off-search.ts` et `off-product.ts`.

**Le problème.** `https://caltrack-ap.netlify.app/api/off/search?q=…` répond à
n'importe qui, sans limite de débit ni contrôle d'origine. Et une **seule**
requête peut déclencher jusqu'à **11 appels** vers Open Food Facts : la
recherche, plus `ENRICH_LIMIT = 10` fiches produit (`Promise.all` dans
`off-search.ts`). Trois conséquences :

1. les invocations de fonctions consomment les **crédits Netlify** (300/mois,
   remis à zéro le 23) ;
2. Open Food Facts peut bloquer les IP partagées de Netlify — ce qui casserait
   la recherche pour toi, exactement le problème déjà vécu en 2.2.2 ;
3. l'application sert de proxy gratuit à n'importe quel tiers.

**Correctif** (par ordre de rapport qualité/effort) :

1. **Limite de débit en mémoire**, quelques lignes, efficace contre les abus
   simples :

   ```ts
   // backend/netlify/lib/rateLimit.ts
   const WINDOW_MS = 60_000;
   const MAX_PER_WINDOW = 30;
   const hits = new Map<string, number[]>();

   /** true si l'appelant a dépassé sa part (30 requêtes par minute). */
   export function isRateLimited(ip: string): boolean {
     const now = Date.now();
     const recent = (hits.get(ip) ?? []).filter((at) => now - at < WINDOW_MS);
     recent.push(now);
     hits.set(ip, recent);
     if (hits.size > 5000) hits.delete(hits.keys().next().value as string);
     return recent.length > MAX_PER_WINDOW;
   }
   ```

   puis, au début de chaque `handler` (l'IP arrive dans
   `event.headers['x-nf-client-connection-ip']`) : répondre `429` avec
   `Cache-Control: no-store`.

   ⚠️ L'état est par instance de fonction, donc approximatif — c'est un
   garde-fou, pas une vraie protection. C'est suffisant pour l'usage visé.

2. **Refuser les requêtes d'une autre origine** : vérifier l'en-tête `Origin`
   et n'accepter que le domaine du site et les prévisualisations Netlify.
3. Baisser `ENRICH_LIMIT` de 10 à 5 : cela divise par deux le pire cas d'appels
   en amont. À arbitrer avec la qualité des résultats (le problème de 2.2.2).

### A-14 — Le cache du service worker n'est jamais purgé

**Où** : `public/sw.js`.

```js
const CACHE_NAME = 'caltrack-v2';   // jamais incrémenté automatiquement
```

**Le problème.** À l'activation, le service worker supprime les caches dont le
**nom** diffère :

```js
keys.filter((key) => key !== CACHE_NAME).map((key) => caches.delete(key))
```

Comme `CACHE_NAME` est figé, aucune purge n'a jamais lieu. Or `/assets/*` est
servi en « cache d'abord » et chaque déploiement produit de **nouveaux noms de
fichiers** (empreinte Vite). Les anciens fichiers restent donc dans le cache
indéfiniment : après des dizaines de déploiements, plusieurs mégaoctets
inutiles sur le téléphone de l'utilisateur, que rien ne libère.

Deux détails mineurs au même endroit :

- `staleWhileRevalidate` lance la mise à jour du cache sans
  `event.waitUntil()` : le navigateur peut arrêter le service worker avant la
  fin de l'écriture ;
- dans `notificationclick`, `data.url` est passé à `new URL(url, origine)` : une
  URL **absolue** l'emporterait sur l'origine. Les notifications sont signées
  (VAPID) et viennent de ton Edge Function, donc le risque est théorique, mais
  n'accepter qu'un chemin relatif coûte une ligne.

**Correctif** — purger les entrées `/assets/` devenues inutiles à l'activation :

```js
self.addEventListener('activate', (event) => {
  event.waitUntil(
    (async () => {
      // Caches d'anciennes versions du service worker
      const keys = await caches.keys();
      await Promise.all(keys.filter((key) => key !== CACHE_NAME).map((key) => caches.delete(key)));

      // Fichiers versionnés qui ne sont plus référencés par la page d'accueil :
      // chaque déploiement change leur nom, les anciens ne servent plus à rien.
      const cache = await caches.open(CACHE_NAME);
      const html = await (await cache.match('/'))?.text();
      if (html) {
        for (const request of await cache.keys()) {
          const path = new URL(request.url).pathname;
          if (path.startsWith('/assets/') && !html.includes(path)) {
            await cache.delete(request);
          }
        }
      }
      await self.clients.claim();
    })()
  );
});
```

Et pour le lien de notification :

```js
const raw = (event.notification.data && event.notification.data.url) || '/';
// On n'accepte qu'un chemin interne
const url = new URL(raw.startsWith('/') ? raw : '/', self.location.origin).href;
```

### A-15 — `calculateMacros` ne garantit pas la cohérence des macros

**Où** : `frontend/features/goals/calculations.ts`, `calculateMacros()`.

```ts
const protein_g = protein_g_per_kg * referenceWeightKg;
const fat_g = Math.max(minFatFromWeight, minFatFromCalories);
const remainingCalories = targetCalories - (protein_g * 4 + fat_g * 9);
const carbs_g = Math.max(0, remainingCalories / 4);   // borné à 0…
```

**Le problème.** Si les protéines et les lipides dépassent déjà la cible, les
glucides sont ramenés à 0 — mais **protéines et lipides ne sont pas réduits**.
La somme `P×4 + L×9 + G×4` peut alors être supérieure à `calories_kcal`, et
l'application affiche des cibles de macros incompatibles avec sa propre cible
calorique.

**✅ Corrigé.**

**Rectification de l'audit.** La première version de cette section disait avoir
cherché un cas atteignable « sans en trouver ». C'était faux : je n'avais testé
que quelques profils à la main. Un test de balayage sur tout l'espace de saisie
autorisé (sexe × taille × poids × âge × type × activité × protéines ×
ajustement) a trouvé **6 cas réels**, par exemple :

```text
F 175cm 80kg 120ans loss act=1.2 prot=2.5 adj=0
  => 1318 kcal de macros pour 1200 kcal de cible
```

Tous à des âges élevés (le problème apparaît vers 95 ans et plus) avec les
protéines au maximum autorisé — rare, mais dans les bornes que l'application
accepte, et avec un objectif par ailleurs ordinaire. Le problème était donc
réel, pas seulement théorique.

**Correctif appliqué.** Le correctif d'abord envisagé (réduire les lipides
seulement) ne suffisait pas : dans les cas trouvés, le minimum de lipides lié au
poids fait lui-même partie du dépassement. On réduit donc dans l'ordre inverse
des priorités :

1. la règle « 25 % des calories » cède d'abord, jamais le minimum lié au poids
   (seuil physiologique) ;
2. en dernier recours, les **protéines** — c'est la valeur choisie par
   l'utilisateur, alors que le minimum de lipides est une contrainte de santé ;
3. le drapeau `macros_reduced_to_fit` signale la réduction, pour que l'interface
   puisse l'expliquer plutôt que de la subir en silence.

Avec, en garde permanente, un test de propriété : pour tout profil et tout
objectif valides, `P×4 + L×9 + G×4 <= calories_kcal + 1` (la tolérance couvre
les arrondis à 0,1 g).

### A-18 — Abonnement push : une adresse arbitraire est acceptée

**Où** : `backend/supabase/migrations/20261108023725_create_push_reminders.sql`.

```sql
endpoint text NOT NULL UNIQUE CHECK (endpoint LIKE 'https://%' AND char_length(endpoint) <= 2048)
```

**Le problème.** Deux petites faiblesses :

1. **Destination libre.** La seule contrainte est « commence par `https://` ».
   Un utilisateur connecté peut donc enregistrer n'importe quelle adresse, et
   ton Edge Function `send-reminders` lui enverra des requêtes. L'application
   devient un petit relais sortant.
2. **Reprise d'abonnement.** `save_push_subscription` fait
   `ON CONFLICT (endpoint) DO UPDATE SET user_id = EXCLUDED.user_id` : qui
   connaît l'adresse d'abonnement d'un autre appareil peut la rattacher à son
   compte — ses rappels partiraient alors vers l'appareil de la victime, qui ne
   recevrait plus les siens.

Le point 2 est **voulu** (c'est ce qui permet de changer de compte sur un même
navigateur, comme le dit le commentaire de la migration) et l'adresse est une
longue URL non devinable : le risque réel est faible. Le point 1 se corrige à
peu de frais.

**Correctif** — restreindre aux services de push connus :

```sql
-- backend/supabase/migrations/<horodatage>_push_endpoint_hosts.sql
-- L'adresse d'abonnement doit appartenir à un service de push de navigateur :
-- sinon l'Edge Function peut être amenée à écrire vers n'importe quel hôte.
ALTER TABLE push_subscriptions DROP CONSTRAINT IF EXISTS push_subscriptions_endpoint_check;
ALTER TABLE push_subscriptions ADD CONSTRAINT push_subscriptions_endpoint_check CHECK (
  char_length(endpoint) <= 2048 AND (
    endpoint LIKE 'https://fcm.googleapis.com/%'          -- Chrome, Edge, Android
    OR endpoint LIKE 'https://updates.push.services.mozilla.com/%'  -- Firefox
    OR endpoint LIKE 'https://web.push.apple.com/%'       -- Safari, iOS
    OR endpoint LIKE 'https://%.notify.windows.com/%'     -- Windows
  )
);
```

⚠️ Vérifier d'abord que les abonnements **existants** passent la nouvelle
contrainte, sinon la migration échoue :

```sql
SELECT DISTINCT substring(endpoint from '^https://[^/]+') FROM push_subscriptions;
```

Documenter aussi le point 2 dans le commentaire de la fonction, pour qu'un
prochain lecteur sache que c'est un choix.

### A-20 — `AuthContext` fait re-rendre toute l'application

**Où** : `frontend/app/contexts/AuthContext.tsx`, fin du composant.

**Le problème.** L'objet passé à `AuthContext.Provider` est reconstruit à
**chaque rendu**, et les fonctions `signUp`, `signIn`, `signOut`,
`updatePassword`, `updateEmail`, `deleteAccount` sont redéfinies à chaque fois
(contrairement à `refreshProfile` et `dismissAuthNotice`, qui sont bien en
`useCallback`). Comme `useAuth()` est consommé très haut dans l'arbre, tout
changement d'état du provider re-rend l'ensemble de l'application, y compris
les composants qui n'utilisent que `user`.

**Correctif** :

```tsx
  const signIn = useCallback(async (email: string, password: string) => { /* … */ }, []);
  // … idem pour signUp, signOut, updatePassword, updateEmail, deleteAccount

  const value = useMemo<AuthContextType>(
    () => ({
      user, profile, loading, profileError,
      signUp, signIn,
      signOut: () => signOut('local'),
      signOutEverywhere: () => signOut('global'),
      refreshProfile, passwordRecovery, requestPasswordReset, updatePassword,
      dismissPasswordRecovery, deleteAccount, updateEmail, authNotice, dismissAuthNotice,
    }),
    [user, profile, loading, profileError, passwordRecovery, authNotice,
     signUp, signIn, signOut, refreshProfile, requestPasswordReset,
     updatePassword, dismissPasswordRecovery, deleteAccount, updateEmail, dismissAuthNotice]
  );

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
```

`AuthContext.test.tsx` (337 lignes) couvre déjà bien ce fichier : il doit
rester vert, c'est le filet de sécurité de ce changement.

### A-26 — Photos orphelines possibles après suppression de compte

`frontend/features/account/AccountSettings.tsx:50` :

```ts
await deleteAllProfilePhotos(user.id).catch(() => undefined);
const { error } = await deleteAccount();
```

Deux conséquences :

1. si la suppression des fichiers échoue (réseau), le compte est tout de même

2. en cas d'échec de `deleteAccount()`, le message affiché est « Aucune donnée

Correctif : signaler l'échec du nettoyage plutôt que de l'avaler, inverser
l'ordre n'étant pas possible (après suppression, plus de session pour écrire
dans le stockage). Ajuster aussi le message. Au passage,
`deleteAllProfilePhotos` liste avec `limit: 100` : suffisant en pratique (une

### A-27 — `fat_g_per_kg_min` n'est pas validé côté client

`GOAL_LIMITS` (`frontend/features/goals/validation.ts`) borne
`protein_g_per_kg` (1,2 – 2,5) mais **pas** `fat_g_per_kg_min`, alors que la
base impose `CHECK (fat_g_per_kg_min >= 0.3 AND <= 3.0)`. Aujourd'hui le champ
n'est pas modifiable depuis l'interface (toujours
`DEFAULT_FAT_G_PER_KG_MIN`), donc c'est sans effet — mais le jour où il le
deviendra, l'erreur remontera sous forme de message Postgres. Ajouter
`fat_g_per_kg_min: { min: 0.3, max: 3 }` et sa validation, par cohérence.

### A-28 — La recherche avancée est transmise telle quelle à l'index

`backend/netlify/functions/off-search.ts`, `buildSearchQuery()` :

```ts
if (ADVANCED_QUERY.test(input)) return input;   // transmis sans transformation
```

Si la saisie contient `:`, `"`, `(`, `)`, `AND` ou `OR`, elle part telle quelle
vers `search.openfoodfacts.org`. C'est voulu (les « produits similaires »
construisent une requête avancée), mais cela veut dire que **n'importe qui**
peut injecter une requête arbitraire dans l'index. L'API est publique et en
lecture seule : aucun risque de fuite. Le vrai effet est fonctionnel — une
requête mal formée renvoie une erreur 400 incompréhensible pour l'utilisateur.

Correctif : ne lever la transformation que pour les requêtes **émises par
l'application** (par exemple un paramètre `mode=similar`) et toujours nettoyer
la saisie libre.

### A-29 — Les pièges de focus ne regardent que les `<button>`

`WhatsNewDialog.tsx:38` et `GuidedTour.tsx` :

```ts
const buttons = Array.from(dialogRef.current.querySelectorAll<HTMLButtonElement>('button'));
```

Un lien, une case à cocher ou un champ ajouté plus tard dans ces fenêtres
sortirait du piège. Le hook partagé proposé en **A-05** règle les trois cas
avec le bon sélecteur.
